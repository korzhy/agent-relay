последний не освобождается автоматически.

## Открытые риски

1. **P1 — report зависит от соблюдения prompt исполнителем.** `agy --print`
   выдаёт текстовый ответ по умолчанию, а Relay принимает только созданный
   исполнителем файл. Локальный `agy 1.2.9` поддерживает `--output-format json`
   и `--json-schema`, но форма ответа и поведение при ошибке ещё не проверены
   на контролируемом реальном запуске. Следующий шаг — исследовать этот
   машинный канал и спроектировать валидируемый fallback; не превращать любой
   текстовый ответ в report.
2. **P1 — публикация нескольких pointer-файлов не является одной транзакцией.**
   `PublishAsync` сначала меняет `control.json`, затем архивирует старые
   `report.json`/`cancel.json`/`failure.json`. Ошибка между операциями может
   оставить новый control и старые pointers. Нужны journal/commit marker и
   fault-injection тесты на каждом шаге.
3. **P1 — не все инфраструктурные исключения runner завершают handoff.**
   Например, отказ FileSystemWatcher, записи runtime/action log или захвата
   process output может оборвать команду вне штатного `FinishAsync`. Нужен
   единый fail-safe lifecycle с остановкой конкретного process tree и
   сохранением причины; нельзя автоматически закрывать handoff, если другой
   runner ещё жив.
4. **P2 — gates остаются заявлением исполнителя.** Структура report и хеши
   проверяются, но Relay не сверяет каждую `--gate` с наблюдаемым результатом
   исполнения. README правильно требует независимой проверки Codex. Для
   усиления нужны точная спецификация gate-команд и внешний verifier;
   синтаксическая проверка `PASS` не доказывает семантическую корректность.
5. **P2 — диагностика и масштабирование.** Dashboard показывает путь к записи
   сбоя, но отдельного экрана с временной шкалой конкретной попытки нет.
   `RuntimeStore.ReadLogAsync`
   читает весь action log, а model/account probes используют `ReadToEndAsync`.
   Нужны ограниченные чтения, ротация и сводка отказа с безопасным просмотром
   stderr без копирования секретов в Git или telemetry.
6. **P2 — fallback модели после ошибки каталога не проверяет её текущую
   доступность.** Кэш/встроенная модель позволяют попытку dispatch, но
   отсутствие модели может проявиться только после запуска. Следует
   различать подтверждённую доступность и аварийный fallback в preflight.

## Практический порядок развития

1. Выпустить и установить исправление issue #1 на обоих ПК; сверить
   `doctor.applicationVersion` и выполнить один контролируемый read-only
   handoff с сохранением failure/report envelope и локальных логов.
2. Закрыть single-channel report transport и инфраструктурные исключения
   runner, затем провести fault-injection по публикации pointer-файлов.
3. Добавить интерфейс диагностики одной попытки и машинно проверяемые gates.
4. Лишь после этого оценивать стабильность по серии запусков: доля
   `reportReady`, причины `stalled`, время восстановления и число ручных
   `cancel/resume`.

Локальные тесты после текущих правок: 90 core и 91 integration, все пройдены.
Это проверка детерминированных сценариев, а не гарантия стабильности реального
Gemini/Windows окружения.
