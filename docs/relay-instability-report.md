# Agent Relay: отчёт о сбоях и нестабильности

Дата фиксации: 2026-09-20

Область: локальная установка Relay и доступный Git checkout

Статус: диагностический отчёт; исправления включены в `v0.5.1`

## Исправлено в v0.5.1

- ожидание стабильного report payload теперь использует пятисекундный deadline
  вместо четырёх попыток примерно за 600 мс и различает `missing`, `unstable` и
  `unreadable`;
- ошибки Credential Manager, недоступные credentials и отказ доступа к локальному
  состоянию больше не схлопываются в `noEligibleAccount`;
- сообщения validation указывают конкретное несовпавшее поле, не ослабляя
  protocol/hash validation;
- `doctor --json` выводит версию и путь запущенного Relay, а также Windows identity
  процесса для сопоставления бинарника и execution context.

## Краткий вывод

Исходники Relay доступны локально в Git. Наблюдаемая проблема выглядит не как
одна подтверждённая ошибка протокола, а как сочетание нескольких границ:

1. установленный бинарник и локальный checkout не совпадают по версии/коммиту;
2. runner считает отсутствие стабильного report payload отдельным исходом после
   debounce/hash validation;
3. report validation намеренно отклоняет payload при несовпадении идентификаторов,
   ревизии, попытки запуска, временной зоны или обязательных полей;
4. один из локальных handoff-review payload’ов подтверждает реальный отказ на
   runtime gate, а не успешную интеграцию.

## Что именно может объяснять сообщения о нестабильности

### 1. Разрыв версий между бинарником и исходниками

Установленная версия `0.5.0+386d8ca6...` новее/отличается от локального
checkout, который находится на `bac3c3c`. Поэтому диагностика по исходникам может
описывать иной runner/protocol lifecycle, чем реально выполняется на этом ПК.

### 2. Узкое окно стабильности report-файла

`AgyRunner` сначала ждёт стабильный файл через `StableFileGate` после debounce и
проверки hash. Если файл отсутствует, меняется или не проходит это окно после
завершения процесса, код формирует исход:
`Runner exited without a stable report payload after debounce/hash validation.`

Это означает, что сам факт завершения внешнего процесса не равен наличию
принимаемого отчёта.

### 3. Строгая валидация протокола

`ProtocolService.ValidateReport` проверяет как минимум protocol version,
`handoffId`, `missionId`, `revision`, `runAttemptId`, UTC offset времени создания,
обязательные коллекции и согласованность PASS/non-PASS claim. Любое расхождение
переводит handoff в отказ валидации даже при наличии JSON-файла.

### 4. Ошибка исполнителя может выглядеть как ошибка Relay

Отклонённый review `relay-jakash-quote-review-r1.json` показывает, что Relay
корректно остановил handoff на независимом runtime-gate. Это не доказывает дефект
самого Relay; это пример того, что отчёт исполнителя мог содержать слишком слабое
доказательство совместимости с реальным runtime.

## Что не подтверждено этим аудитом

- Не найден локальный артефакт, который однозначно доказывает конкретный stalled
  handoff по ID и времени.
- Не доказано, что именно `--output-format json` устраняет или вызывает сбои;
  это отдельное незакоммиченное изменение, требующее самостоятельной проверки.
- Не доказана причинность между расхождением версий и каждым отдельным отказом
  report validation.

## Наше техническое мнение

Приоритетная причина для устранения неопределённости — сначала обеспечить
сопоставимость бинарника и исходников (точный commit/build), затем собирать
диагностику одного handoff по полному набору: control envelope, runner exit,
временная шкала изменений report-файла, stable-file hash и сообщение
`ValidateReport`. Без этого сообщения `stalled` и `runner exited without stable
report payload` остаются разными симптомами, которые нельзя надёжно объединять в
одну причину.

Следующий безопасный шаг — read-only воспроизведение на тестовом checkout с
сохранением временной шкалы и payload hashes. Не следует пока менять протокол,
ослаблять validation или считать наличие JSON-файла доказательством успешного
handoff.
